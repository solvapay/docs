In sandbox, enter a SolvaPay test card on the card step of Checkout, the customer portal or the SDK card fields. Use any future expiry date and any security code (4 digits for American Express).

The same numbers work whichever payment processor runs your account, so your tests never change when the processor does. Test cards are refused in live mode, and a real card never behaves like a test card.

## Card numbers

The first eight digits pick the brand and funding type. The three digits before the last one pick the scenario, and the last digit is the check digit.

| Brand and funding | Starts with | Succeeds | Stripe |
| --- | --- | --- | --- |
| Visa credit | `4111 5700` | `4111 5700 0000 0018` | Yes |
| Visa debit | `4111 5800` | `4111 5800 0000 0017` | Yes |
| Visa prepaid | `4111 5900` | `4111 5900 0000 0016` | Not yet |
| Mastercard credit | `5454 5700` | `5454 5700 0000 0010` | Yes |
| Mastercard debit | `5454 5800` | `5454 5800 0000 0019` | Yes |
| American Express | `3782 5700` | `3782 570000 00018` | Yes |

A scenario that is not available yet is refused with `scenario_not_supported_by_processor`, so a test never passes by accident. A number with a test prefix and an unknown scenario code is refused too.

Scenarios `601` to `606` concern the saved card rather than the payment: the payment succeeds, and once the card is saved the outcome is applied to it as the card network would report it.

## Server-side tests

To confirm a payment intent with a `paymentMethodId` instead of a captured card, pass `spm_test_<scenario>` in sandbox, for example `spm_test_success` or `spm_test_decline_insufficient_funds`. It behaves like the Visa credit test card for that scenario. Named test payment methods are refused in live mode.
